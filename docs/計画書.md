## 1. 目的と背景（1ページ）

### 1.1 止まったサイトと市民の不便（報告書「長く止まったのは…」の要約）

- 2024〜2026年に日本で週単位以上止まったのは、会員・決済・受発注を持つ「取引の場所」だった（ニコニコ 2024-06-08〜08-05、アスクル／LOHACO 2025-10-19〜2026-01-20、アサヒの受注 2025-09-29〜12月）。第三者は代わりを作れない。確認済み。
- 短く広く効いたのは DDoS。tenki.jp は 2025-01-05・09・15 にウェブ版とアプリ版が見づらくなった（日本気象協会の告知）。気象庁のサイトも 2021-08-14 の大雨でアクセスが集中して見づらくなった。確認済み。
- 2022年の KDDI 通信障害の調査で、利用者の19.5%が「障害・復旧状況を知りたかったがデータ通信できなかった」と答えた（通信障害のデータで、Web の停止に同じ割合が当てはまるかは未確認）。
- 内閣サイバーセキュリティセンターは 2025-02-04 の注意喚起で「ソーリーページを別サーバーに用意する」ことを挙げた。確認済み。
- 停止の日の注目は Wikipedia 閲覧数で平常の約12〜200倍に跳ねた（コミックシーモア 約12〜18倍、日本気象協会 1月9日に約27倍、IDCフロンティア 約200倍。報告書）。多くは3〜5日で数分の一に減る。Google トレンドと X の履歴は読めなかった。
- tenki.jp の停止中に気象庁へ人が流れた形跡は、Wikipedia 閲覧数からは見えなかった（報告書）。第1号の需要の根拠は弱い（2.0 の「想定アクセス」）。

### 1.2 この第1号が解く問題

民間の天気サイトや気象庁のサイトが重い・止まっている時間に、**気象庁の発表を1文字も変えずに、発表時刻と取得時刻つきで、別系統の配信から軽く出す**。気象庁自身が止まった場合は「最後に取得できた発表」を古さ込みで見せることしかできない（報告書「第1号は…」）。付加価値はこの1点に限られる。

## E.6 `site/sources.json` の書き方

```json
{
  "sources": [
    {
      "id": "outages",
      "name": "（出典の名前）",
      "url": "https://（再配布が許されたデータの URL）",
      "format": "csv",
      "encoding": "cp932",
      "license": "公共データ利用規約（第1.0版）",
      "license_url": "https://（利用規約の URL）",
      "attribution": "出典: （出典表示の文言をそのまま）",
      "timeout_seconds": 20,
      "max_bytes": 2000000,
      "max_drop_ratio": 0.5
    }
  ]
}
```

- `format` は `json` か `csv`（見出し行つき）。JSON の中の場所は `items_path` で、鍵（文字列）と添字（0以上の整数）の並び
  （例 `[0, "timeSeries"]`）。一番外がオブジェクトで1件の表なら `"shape": "object"`。
- `report_time_path`（任意）: 発表時刻の場所（ISO 8601。`+09:00` か `Z` つき）。あれば、前回より古い発表を unreadable に倒して
  前回分を保ち、取得状況のページに元の発表時刻を出す。時刻が無い・時差が無いものも unreadable。
- `each`（任意）: `{"code": ["130000", "270000"]}` で、`url` の `{code}` を値ごとに置き換えた取得先に展開する
  （id は `<id>-<code>`）。府県予報区のように同じ形のファイルが多いとき、手で百数十行を書かない。
- 取得は同時4本まで・全体の締切600秒（`fetch.py --max-workers`・`--deadline-seconds`）。締切を過ぎた取得先には行かず
  unreadable にして前回分を出す（元のサイトが重い日＝出番の日に、ジョブが終わらず何も公開できなくなるのを防ぐ）。
- 転送は辿らない（url には転送先の https の URL を書く）。1つの取得先で何が起きても全体は止めず、その取得先だけ unreadable。
- CSV は `columns`（見出しに必ずある列）が必須（エラーページの HTML を CSV と読んで「0件」にしないため）。
- `format: "xml"`: 標準の xml.etree で読み、**DOCTYPE・ENTITY を含む XML は読まない**（実体の展開で膨らませる攻撃を、expat の
  版に頼らず入口で断つ）。名前空間を外した dict にする（属性は `"@名前"`、文字は `"#text"`、子は名前ごとに必ず並び）。
  Atom のフィードなら `items_path: ["entry"]`・`report_time_path: ["updated", 0, "#text"]`。
- `heartbeat`（任意）: 見張り役の取得先の id。見張り役が unreadable（読めない・古い）なら、これを付けた取得先も「新しさを確かめられない」
  として unreadable にし、データは前回の内容として出す。★発表時刻の見張り（`max_report_age_hours`）は、静かなときに何日も更新されない
  取得先（官署ごとの警報など。静かな官署は66〜78時間更新が無いのが正常）には付けず、全国のスナップショット（フィード自体の updated など）を
  見張り役にして、それに `heartbeat` でつなぐ。見張り役に `heartbeat` は付けない（連鎖させない）。
- 公開する `data/<id>.json` には出典（`source`: name・url・license・license_url・attribution）が入る（JSON の写しにも出典と利用条件が付く）。
- `format: "custom"`: fetch.py は取りに行かない。**二段の取り込み**（フィード→各電文）は `tools/fetch_<名前>.py` に分けて作り、
  `fetch.merge_records()` で記録を足す。その決まり（新しいリポジトリの CLAUDE.md の掟6b）: ①辿ってよいのは、コードに定数で書いた公式の置き場の
  前置き（https）で始まるリンクだけ ②1回に辿る数の上限 ③取り込み済みの電文は URL で前回分から使い回す ④1つでも読めなければ、その取得先は
  全体を unreadable（一部の官署だけ抜けた表示は「警報なし」に読める） ⑤取得は `fetch.http_get`・XML は `fetch.parse_xml` ⑥試験と検算。
- 任意の見張り: `required_keys`（JSON の各行に必ずある鍵）・`min_items`（件数の下限。直前比の急減を少しずつ繰り返す
  減り方に効く）・`max_report_age_hours`（発表時刻がこれより古ければ unreadable。★元が黙って止まったときの見張り。
  2026-10-23 に、気象庁 bosai の警報 JSON が 2026-05 末から更新されていないのを実測した。取得は成功し件数も減らないので、
  これが無いと「取れた」に見える）。
- 日本の官公庁の CSV は Shift_JIS が多い → `encoding: "cp932"`。
- `max_drop_ratio`: 前回より5割を超えて減ったら「形式が変わった」とみなして unreadable にし、前回分を保つ。
  本当に0件になりうるデータ（例: 障害がすべて解消）なら `1.0` にして見張りを外す。
- `id` はファイル名になるので英小文字・数字・`-`・`_` だけ（パスの外へ出られない）。

## E.7 型Aと型Bの差（どちらに転んでも使えるように）

| | 型A（標準） | 型B（`/api/*` だけ Worker のコード） |
|---|---|---|
| データの新しさ | 30分ごと（GitHub の定期実行。遅れうる） | 利用者が開いた時（縁で60秒使い回す） |
| 無料の上限 | 静的アセットへの要求は無料・無制限 | Worker が動く要求は Free で1日10万回。超えると `/api/*` は 429 になる（公式）。静的アセットがそのあと配られ続けるかは明記なし |
| 安全のヘッダ | `_headers` で付く | ★Worker の応答には `_headers` が効かない → コードで付ける（見本に入れてある） |
| 縁での使い回し（Cache API） | 不要 | 公式文書が「動く」と書くのは独自ドメインだけ → ★独自ドメインを付けてから型Bにする |
| 元のサイトへの負荷 | 30分に1回 | データセンターごとに使い回すので、全体では毎秒数回になりうる。元が弱いなら型Aのまま |
| 中継の踏み台にならないか | 取りに行く先は sources.json に固定 | 取りに行く先はコードに1つだけ固定。利用者のクエリやパスで URL を作らない |
| 秘密 | Cloudflare のトークンだけ | 元の API のキーが要るなら `wrangler secret put`（リポジトリにも CI にも置かない） |
| 足すもの | — | `docs/型Bへの差分.md`（`src/worker.js`・Node の試験・wrangler.jsonc の差分・CI の1手） |

★型Bでも型Aの取り直しは残す（エッジ関数が読めなかった時に「前回の内容」として出す受け皿）。

## 掟（理由つき）

1. **非公式を隠さない。** 全ページの先頭に「非公式」の帯（`data-unofficial-banner`）。止まったサービスの名前を
   サイト名・ドメインに入れない。ロゴ・配色・画面の作りを真似ない。公式を名乗らない。
   （事件の最中は偽の代替サイト＝フィッシングが実際に出る。こちらがそれに見えてはいけない）
   帯の見た目は `banner.css` だけで決め、中身は check_dist.py が固定している。ほかの CSS で帯を狙わない・
   見えなくする指定（display:none など）を使わない。帯の中で hidden を使えるのは「更新が止まっています」の欄だけ。
2. **入力を受けない。** form・ログイン・決済・Cookie・端末への保存を作らない（集めなければ漏れない）。
   **軽く作る。** 1ページ（HTML＋読み込む CSS・JS・画像）300KB 以下・画像1枚 200KB 以下（check_dist.py が見張る）。
3. **外部の JS・CSS・フォント・画像・解析タグ・広告を読み込まない**（CSP が止め、`tools/check_dist.py` が落とす）。
   入れたくなったら、実装せずに店主へ訊く（CSP と check_dist.py の方針を変える話になる）。
4. **HTML を文字列で組み立てない。** 外から来た値は `common.esc()` を通す。JS は `textContent` と
   `createElement` だけ（`innerHTML` は Trusted Types で止まり、check_dist.py も落とす）。
   HTML にコメント（`<!--`）・CDATA・インラインの `<svg>`・`<template>`・`<noscript>` を書かない（ブラウザと検査器で
   読み方がずれ、中に `<script>` を隠せる）。`_redirects` を置かない（全ページを別のサイトへ飛ばせる）。
5. **三状態**: ok（取れた）/ empty（元が0件）/ unreadable（取れない・形が変・急減・発表時刻の後戻り・時間切れ）。
   ★unreadable を「0件」「無い」と描かない。空で上書きしない（前回分を「前回の内容」と明記して出す）。
   ★更新が止まったことは `site/static/freshness.js` が閲覧者の時計で言う（静的な HTML だけでは言えない）。消さない。
6. 取りに行くのは `site/sources.json` に**利用条件（license・license_url・attribution）を書いた出典だけ**。
   規約で禁じられた取得をしない。止まったサイトの文章・画像を写さない。転送は辿らない（url は転送先を書く）。
   CSV には `columns`（見出しに必ずある列）を書く。JSON の行の形は `required_keys`、元が黙って止まるのは
   `max_report_age_hours`、少しずつ減るのは `min_items` で見張る（計画書の付録E E.6）。
   XML は `fetch.parse_xml()` だけで読む（DOCTYPE・ENTITY を含む物は読まない）。全国の見張り役は `heartbeat` でつなぐ。

   `site_hooks.pages`、サイト専用の関所は `site_hooks.check_dist`（`data_dir` は build の作業場の `data/`）・`check_repo`・
