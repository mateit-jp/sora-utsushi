# 運用（店主の初回の手順・ふだんの流れ・止まったときの見方）

## 0. 何がどこで動くか

```
GitHub（コード・PR の検査・30分ごとの取り直し）──deploy──▶ Cloudflare（配信。<名前>.<アカウント>.workers.dev）
        ▲                                                     │
        └──── 外の見張り（任意）: tools/check_live.py を1日1回 ◀┘
```

## 1. 初回だけ店主がすること（2回目以降は無し）

| # | どこで | 何を | 備考 |
|---|---|---|---|
| 1 | GitHub | このリポジトリを持つアカウントで、2要素認証（パスキー推奨）が有効か確かめる。サイト専用のアカウントにするなら、ここで作る | ★以下の GitHub の操作（gh・画面・Claude GitHub App）は、すべてこのアカウントで行う。別のアカウントで行うと、その名前が公開のリポジトリ（PR・コメント・実行の記録）に出る |
| 2 | この Mac の端末 | `! brew install gh` → ブラウザでこのリポジトリを持つアカウントに入った状態で `! gh auth login -h github.com -p https -s workflow -w` → `gh api user --jq .login` がそのアカウント名か確かめる | ★`-s workflow` が無いと `.github/workflows` を push できない。★ブラウザが別のアカウントのままだと、そちらが gh に入る（gh に複数のアカウントが入っているなら `gh auth switch` で切り替える。`repo_settings/*.sh` は、管理者でないアカウントでは何もせずに止まる） |
| 3 | この Mac（Claude に頼む） | リポジトリを public で作り、雛形を push → `sh repo_settings/apply.sh OWNER/REPO` → `sh repo_settings/check.sh OWNER/REPO` | 作る前に `gh api user --jq .login` が OWNER か確かめる（違うアカウントのまま作ると、そのアカウントの下に公開のリポジトリができる）。コミットの作者は、このリポジトリの中だけで `git config user.name OWNER`・`git config user.email <ID>+OWNER@users.noreply.github.com`（ID は `gh api user --jq .id`。`--global` は付けない）。画面で入れるなら `docs/リポジトリの設定.md` |
| 4 | Cloudflare | アカウントを作る（2要素）→ Workers & Pages で Worker を1つ作る（名前＝`wrangler.jsonc` の `name`。中身は Hello World でよい）。このとき workers.dev のサブドメインを決める | ★Worker を新しく作るには全 Worker の Admin 権限が要る。店主が画面で作っておけば、CI のトークンは「その Worker だけの Editor」で済む |
| 5 | Cloudflare | API トークンを作る: Workers の **Editor** を **その Worker だけ**に | Admin（全 Worker）や旧「Workers Scripts Edit」（アカウント全体）にしない。IP 制限は付けない（GitHub の実行機の IP は毎回変わる） |
| 6 | この Mac の端末 | `! gh secret set CLOUDFLARE_API_TOKEN --env production --repo OWNER/REPO`（値は貼るだけ）／`gh variable set CLOUDFLARE_ACCOUNT_ID --env production --repo OWNER/REPO --body <ID>` | トークンの値はどこにも書き残さない |
| 7 | GitHub | このリポジトリを持つアカウントで、Claude GitHub App をこのリポジトリ**だけ**に入れる（https://github.com/apps/claude/installations/new） | クラウドの Claude Code が使う。★クラウドの PR は、claude.ai につないだ GitHub のアカウントの名前で出る見込み（未確認。最初の PR で作者を見る）。このリポジトリを持つアカウントにつなぐ。別のアカウントを共同作業者に足してつながない（その名前が公開の PR に出る） |
| 8 | GitHub | Actions → deploy → Run workflow（初回の公開） | build → deploy → verify が全部緑なら完了 |

`site/config.json` の `site_url` は `https://<Worker 名>.<サブドメイン>.workers.dev/`（末尾の `/` まで）。

## 2. ふだんの流れ

- クラウドの Claude Code が PR を出す → CI（test・wrangler-dry-run・zizmor）が緑 → 店主が **Squash and merge**
  → main への push で deploy（build → deploy → verify）。
- verify は、ヘッダ・「非公式」の帯・404・status.json の鮮度に加えて、**公開中の全ファイルが今作った物と1バイトも
  違わないか**を照合する（CDN 側の書き換えや、検査を通っていない版の公開に気づくため）。別のホストへの転送も違反にする。
- deploy ジョブは、受け取った物を公開の直前にもう一度 `check_dist.py --production` で検査してから公開する。
- ★関所（`tools/`・`.github/`・`site/headers.json`・`banner.css`・`freshness.js`）を変える PR は、マージの前に差分を見る。
  承認0の ruleset では、PR が関所そのものを書き換えられる（関所が止めるのは「うっかり」だけ）。
- 30分ごと（毎時13分・43分。混む0分を避けた）にデータを取り直して公開し直す。
- Dependabot の PR（週1回・月曜9時・出て7日たった版だけ）は、CI が緑ならマージ。
  ★マージはリポジトリの「活動」にもなる（GitHub は「活動」の定義を書いていないので推測）。

## 3. 黙って止まる経路と見張り

| 経路 | 何が起きる | どう知る |
|---|---|---|
| 60日無活動 | public リポジトリの定期実行を GitHub が自動で止める（state が `disabled_inactivity`）。**失敗メールは来ない** | `check_live.py --repo OWNER/REPO` が workflow の state を見る／status.json が古くなる |
| 定期実行の遅れ・取りこぼし | 毎時0分前後は遅れ・落ちることがある | status.json の鮮度（既定180分）を verify と外の見張りが見る |
| 取得先の停止・形式の変化 | unreadable（前回分を表示し、取得状況のページに理由） | Actions の黄色の注記・取得状況のページ・`--max-source-age-minutes` |
| トークンの取り消し・権限不足 | deploy ジョブが赤 | Actions の失敗メール（cron を最後に変えた人へ届く） |
| Cloudflare 側の変化 | ヘッダが付かない・何でも 200 を返す等 | verify ジョブ（check_live.py）が赤 |

**外の見張り（店主が選ぶ）**

1. 店主の手元の毎朝の点検に1行足す（推奨）:
   `python3 -I tools/check_live.py https://<公開URL>/ --repo OWNER/REPO --max-source-age-minutes 720`
   → 赤（終了コード1）か読めない（2）なら1日1通。★2 を「問題なし」と扱わない。
2. 何もしない（Actions の失敗メールだけ）。★60日無活動の停止には気づけない。

乗っ取りを疑うとき・何かが壊れたときの順番は `docs/障害対応.md`（1枚）。

## 4. 戻す（ロールバック）

- いちばん確実なのは、PR で直して main に入れること。
- 急ぐとき: Cloudflare の画面で、その Worker のデプロイの一覧から前の版へ戻す（または店主の端末で `npx wrangler rollback`）。
  ★戻したあと、次の定期実行が main の版で上書きする。main も必ず直す。

## 5. トークンが漏れたかもしれないとき

1. Cloudflare の API トークンの画面で、そのトークンを作り直す（Roll）か消す。
2. `gh secret set CLOUDFLARE_API_TOKEN --env production --repo OWNER/REPO` で新しい値を入れる。
3. Cloudflare の監査ログで、身に覚えのないデプロイが無いかを見る。

## 6. 独自ドメインを付けるとき（後で・店主が決める）

- 止まったサービスの名前や紛らわしい綴りを入れない（なりすまし・商標）。
- Workers の独自ドメインは、そのドメインのゾーンを Cloudflare に置く必要がある。
- ★ゾーンを置くと、Free でも RUM（Web Analytics のビーコン）が自動で入ることがある。切る（外部送信になり、CSP でも止まる）。
- HSTS の `preload` は付けない（戻せない）。レジストラの2要素・ロック・DNSSEC を入れる。
- 付けたら `wrangler.jsonc` の `workers_dev` を `false` にするかを決める（workers.dev 側に古い URL を残さないため）。
